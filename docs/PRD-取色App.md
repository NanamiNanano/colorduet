## 1. 结论先行（可行性摘要）

**总体结论：可行，工程风险中等，最大的不确定性不在"能不能做"，而在"RYB 用什么口径定义"和"Android 打包链路的稳定性"。**

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 功能可实现性 | ✅ 高 | 四项核心功能（双色环、图片取色、色卡列表、存档）均为成熟图形交互，无算法级难题 |
| 技术栈匹配度 | ⚠️ 中 | Python 做移动端图形 App 可行，但需接受包体大（35–60 MB）、启动慢（1–3 s）、构建链脆弱 |
| RYB 模型严谨性 | ⚠️ 中 | RYB 无官方标准，必须自定算法并明确告知用户"估算值"，否则用户会质疑数值 |
| Android 构建链路 | ⚠️ 中 | Python 打 Android 包只能在 Linux/macOS 或 CI 上做，Windows 本地必须靠 GitHub Actions；首次构建 20–40 min |
| 交互体验风险 | ⚠️ 中 | 手指遮挡导致取色不准，必须有放大镜；二维色环无法表达明度，必须补滑杆 |
| PC 本地测试版 | ✅ 高 | 同源代码在 Windows 直接运行，是降低试错成本的关键设计 |
| 工作量估算 | 26–38 人日 | 单人全职 6–8 周；业余开发按 2–3 个月排 |

**三条最关键的判断（建议在评审时确认）**

1. **必须做"色彩内核"与"UI"解耦**。色环纹理生成、RGB↔RYB 换算、ΔE 计算全部写成不依赖 Kivy 的纯 Python 包，PC 端与 Android 端共用，CI 里可以跑单元测试。这是整个方案可测、可交付的地基。
2. **色环必须是"色环 + 明度滑杆"**，而不是只有色环。二维色环最多表达色相+饱和度两维，用户想要的深红、藏蓝、米白都取不到。这是原始需求里最容易翻车的点。
3. **RYB 数值要预先定义清楚"这是什么"**。它是"颜料估算量"，不是国际标准色彩空间。界面上需要一句话说明（或 `?` 气泡），否则后期会被反复质疑。

## 2. 背景与目标

### 2.1 问题

设计师、插画师、手工/手作从业者在实际工作中有两类割裂的动作：

- **屏幕场景**（找参考图、取品牌色）：用吸管工具取色，但拿到的是一串 HEX/RGB，靠肉眼猜"这个色偏暖还是偏冷、和上一个色差多少"。
- **颜料场景**（调色、选笔、选布料）：脑袋里想的是"红加黄偏橙、再加点蓝会变灰"，这是**RYB（红黄蓝）**体系，而所有取色工具只给 RGB/HSV，两者之间没有桥。

结果就是：取色工具给的是"光的数值"，而人需要的是"颜料的直觉"。

### 2.2 产品目标

做一款**同时用两种色彩语言说话**的取色工具：从图片里取到真实像素色，既能给出精确的 RGB 数值，也能立刻告诉你它在**美术红黄蓝色环**上的位置、相当于多少红/黄/蓝颜料、明度多少。并且可以把取到的色卡存成可命名、可排序、可回溯的"色板项目"。

### 2.3 目标用户与场景

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| 插画师 / 画师 | 看到参考图，想临摹它的配色 | 从图取色 → 换算成颜料直觉 → 记录成色板 |
| UI/平面设计师 | 定主色、配辅助色、检查对比度 | 快速存色、命名、排序、比对差值 |
| 手作/服装/家居 | 拍照找相近颜料或布料色 | 用 RYB 视角描述颜色，判断"该往哪个方向调" |
| 爱好者 | 玩色环、做配色卡片 | 界面直观、操作跟手、可分享 |

### 2.4 成功标准（MVP 阶段）

- 从打开 App 到取出第一个颜色并加入色板，**≤ 4 次操作、≤ 15 秒**。
- 图片取色点到即得，**点击到色环标记更新 ≤ 100 ms**。
- 色环拖动、图片缩放**稳定 ≥ 30 fps**（中端机 4 GB 内存）。
- 存档后杀进程重开，**图片与色板 100% 还原**。
- 数值自洽：色环取色 → 存入色板 → 读档重开，RGB 与 RYB 数值三处一致（允许 ±1 量化误差）。

### 2.5 非目标（本版本明确不做）

- 云同步、账号体系、社区分享平台。
- 相机**实时**取色（取景器逐帧取样），仅做"拍照后取色"。
- 印刷级色彩管理（ICC 特性档、专色 Pantone 库授权、CMYK 转换）。
- iOS 版本。
- 多图层/多画布编辑。

## 4. 核心概念与色彩模型定义（本方案最关键的一章）

> **2026-10-29 已修订**：本章的模型框架已被 [`设计方案-色彩模型与比较.md`](设计方案-色彩模型与比较.md) 替代。
> 主要变化：① 双环语义由"加色/减色"改为"光混合/颜料混合"（CMY 的补色与 RGB 重合，不可用作第二环）；
> ② 光色环色相角改用 OKLCH（感知均匀），HSV 仅作内部换算；③ 数值降级，主显示改为"位置 + 与参照色的差值"。
> 下文 4.4 的颜料立方体插值与 4.5 的反解方法**仍然有效**，继续沿用。

### 4.1 三个模型各自负责什么

| 模型 | 作用 | 是否显示给用户 |
| --- | --- | --- |
| **RGB / HSV** | 屏幕真实颜色；HSV 用于驱动 RGB 色环的几何（角度=色相，半径=饱和度，滑杆=明度） | 显示 RGB 三元组 + HEX |
| **RYB 颜料立方** | 红黄蓝颜料混合的近似光学结果；把"颜料直觉"翻译成屏幕颜色 | 显示 RYB 三元组（估算） |
| **显示柱坐标（色环几何）** | 把上面两者统一成"角度+半径+明度"，才能画成环 | 不显示，仅用于定位 |

### 4.2 RGB 模式色环的几何定义

标准 HSV 环，**固定明度 V（由滑杆控制）**：

- 角度 θ：0° = 红，60° = 黄，120° = 绿，180° = 青，240° = 蓝，300° = 品红。刻度标注为 `R / Y / G / C / B / M`（加色体系，第二色是黄、青、品红）。
- 半径 ρ：0 = 圆心（灰/白，取决于 V），1 = 最外圈（全饱和）。
- 明度 V：由色环右侧竖直滑杆控制，0–100%。
- 取色公式：`(H,S,V) = (θ/360, ρ, V)` → RGB。

### 4.3 RYB 模式色环的几何定义

同样的圆，**换一套语义只有第一环不同，其余结构一致**，避免用户切换模式后找不到北：

- 角度 θ：0° = 红，60° = 橙，120° = 黄，180° = 绿，240° = 蓝，300° = 紫。刻度标注为 `R / O / Y / G / B / V`（减色体系，第二色是橙、绿、紫）。
- 半径 ρ：0 = 圆心（无颜料/灰），1 = 最外圈（纯颜料）。
- 明度 L：同一根竖直滑杆（0 = 全黑，1 = 全白/最亮）。

**注意**：两模式的环在几何上完全一致，只是"角度到颜色"的映射函数不同。这一点要在交互上明确提示（切换时环上标签与颜色一起渐变，而不是整环突变）。

### 4.4 RGB → RYB 正向换算（颜料混合近似）

采用**三角棱柱 / 立方体三线性插值**的经典做法（Gossett & Chen, 2005 的"Paint Inspired Color Mixing"），即把 RYB 看成单位立方体的三个坐标，立方体 8 个角点对应已知颜色，任意 RYB 值由 8 个角点三线性插值得到 RGB：

| RYB 角点 (R,Y,B) | 含义 | 参考 RGB（**需在实现阶段校准**） |
| --- | --- | --- |
| (0,0,0) | 白 | (255,255,255) |
| (1,0,0) | 红 | (255,0,0) |
| (0,1,0) | 黄 | (255,255,0) |
| (0,0,1) | 蓝 | (42,95,153) |
| (1,1,0) | 橙 | (255,128,0) |
| (1,0,1) | 紫 | (128,0,128) |
| (0,1,1) | 绿 | (0,168,51) |
| (1,1,1) | 黑（褐黑） | (51,24,0) |

> 说明：这张角点表是**可调参数**，不是常数。落地时必须做一轮肉眼校准（例如"红+黄=橙"要真的偏橙，别偏粉）。文档里的数值只作为起点，评审时无需纠结小数位。

**重要性质**：在这个立方体里，`(0,0,0)` 是白、`(1,1,1)` 是黑，所以立方体主对角线就是灰轴。于是可以顺理成章地定义 RYB 的三个"人话"分量：

- 明度 `L = 1 - (r+y+b)/3`
- 彩度 `C = max(r,y,b) - min(r,y,b)`
- 色相角 `θ`：由"去灰后"的颜料向量合成方向决定（三个颜料在环上间隔 120°）

这套定义的好处是**可逆、自洽、无奇异点**：给定 (θ, ρ, L) 可以解析地反解出 (r,y,b)，不会出现"取色后算不回去"的尴尬。

### 4.5 RYB → RGB 反向换算（从像素色求颜料量）

用户点了一个像素，得到 RGB，要回答"这相当于多少红黄蓝、在环上哪"。这是**反问题**，没有解析解，方案：

1. 预生成 RYB 立方体的采样网格（如 17×17×17 = 4913 个点），每点用 4.4 的正向公式算出 RGB。
2. 运行时在该网格中做**最近邻 + 局部细化**（在 CIELAB / OKLab 里算距离，比 sRGB 欧氏距离更接近人眼），取误差最小的候选。
3. 处理**多解**：不同 RYB 可能混出同一个 RGB（例如"少量红+黄+一点蓝"和"灰+一点橙"）。规则：同误差范围内优先取**彩度高**的解，其次优先与当前模式色相角连续性最好的解，避免标记在环上乱跳。
4. 量化误差必须可接受：目标 **ΔE00 ≤ 3**（肉眼基本无感），并在文档与测试里固化这条验收线。

**性能预算**：4913 个候选的批量距离计算，numpy 向量化约 1–4 ms，点选是离散操作，完全够用；不必上 KD-Tree，也不必上 scipy（Android 上 scipy 打包体积与兼容性都是负担）。

### 4.6 无彩色 / 边界规则（必须写清，否则必出 bug）

| 输入 | 色环标记位置 | 数值显示 | 提示 |
| --- | --- | --- | --- |
| 纯灰（r=g=b） | 圆心 | S=0 / RYB 彩度=0，RGB 正常显示 | 环上标注"无彩色" |
| 纯黑 #000000 | 圆心，外圈为暗色环 | L=0 | 色相为"未定义"，不显示角度 |
| 纯白 #FFFFFF | 圆心 | L=1 | 同上 |
| 高饱和但极暗（如 #100008） | 按下式计算得到角度，但标记加"低亮度"角标 | 正常 | 避免用户以为取色失败 |
| 低饱和（S < 5%） | 圆心附近，允许吸附到圆心 | 正常 | 吸附阈值可在设置里关 |

### 4.7 数值口径（用户看到的到底是什么）

| 项 | 口径 | 示例 |
| --- | --- | --- |
| RGB | 0–255 整数三元组 + `#RRGGBB` | `RGB(33, 150, 243)` `#2196F3` |
| RYB | 0–100 的整数三元组（百分比，三者不要求和为 100） | `RYB(12, 35, 54)` |
| 附加（P1） | 色相角（0–360°）、明度 L（0–100%） | `H 210° / L 47%` |

> RYB 三项**不归一化**：归一化会让"这个色颜料很浓"的信息丢失，用户按百分比理解即可。

## 5. 功能需求

优先级：**P0** = MVP 必须；**P1** = 首个正式版；**P2** = 后续迭代。
每条需求的验收标准都写成"可测的句子"，避免"体验流畅"这类空话。

### 5.1 色环模块（Wheel）

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| FR-W1 | P0 | RGB / RYB 双色环，一键切换，记住上次模式 | 切换 ≤ 300 ms；标签与环色同步过渡；杀进程重开仍为上次模式 |
| FR-W2 | P0 | 环上任意位置点选/拖动取色，标记跟随手指 | 标记中心到手指投影点偏差 ≤ 4 px；拖动时 ≥ 30 fps；抬手后保持位置 |
| FR-W3 | P0 | 明度滑杆（0–100%），与色环联动 | 滑杆变化时环整体明暗实时变化（≤ 120 ms 更新），标记位置不变、颜色更新 |
| FR-W4 | P0 | 实时颜色预览区：大色块 + 上一色对比 | 预览色与标记色一致（逐像素相等）；显示"新/旧"叠放对比 |
| FR-W5 | P1 | 环上 6 个主刻度点标注 + 可开关 | 标签不遮挡标记；字号随环尺寸缩放 |
| FR-W6 | P1 | 数值输入：可编辑 HEX / RGB / RYB，回车应用并反向定位标记 | 非法输入不崩、给出内联提示；输入合法则标记精确落到对应位置 |
| FR-W7 | P0 | 无彩色与纯黑白的定位与提示 | 按 4.6 表逐行通过 |
| FR-W8 | P1 | 色环直径自适应屏幕，横竖屏均不变形 | 竖屏宽屏切换后环为圆（长宽比偏差 ≤ 1%），标记相对位置不变 |

**关键交互补充（容易漏）**

- **按住环外拖动**也算调整色相（很多人习惯从环内划出去），不要中断。
- 环中心留一个"灰点"，长按环中心 = 直接取中灰，比精准点圆心容易。
- 双指在环上做**缩放**无意义，禁用以避免与图片手势冲突；环上只响应单指。

### 5.2 图片取色模块（Image）

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| FR-I1 | P0 | 从相册/文件导入图片（jpg/png/webp） | 10 MB / 4000 px 图导入 ≤ 1.5 s；失败有明确提示（格式、损坏、内存） |
| FR-I2 | P0 | 双指缩放、单指平移、双击复位、边界限制 | 缩放 0.2×–20×；缩到最小时不出现大片空白；平移不越界超过 1/3 屏 |
| FR-I3 | P0 | 点击图片取像素色，并**同步更新色环标记与预览** | 点击到标记更新 ≤ 100 ms；取色点显示 1 个短暂十字动画 |
| FR-I4 | P0 | **长按放大镜精选取色**：长按出现 5× 放大镜（带十字 + 色块实时预览），拖动微调，抬手确认 | 放大镜中心 = 最终取色点（偏差 ≤ 1 像素）；放大镜跟随手指且不遮挡取色点 |
| FR-I5 | P1 | 已取色点在图上留标记（编号小圆点），可一键隐藏 | 标记与缩放平移同步移动；隐藏后不绘制 |
| FR-I6 | P1 | 采样方式：单像素 / 3×3 均值 / 5×5 均值（默认单像素） | 三种模式结果可分别复现；均值用于噪点图 |
| FR-I7 | P1 | 图片预处理：EXIF 方向纠正、超大图降采样、HEIC 支持 | 旋转拍摄的照片方向正确；6000 px 图不 OOM；HEIC 不支持时给出可读提示 |
| FR-I8 | P0 | 图片取色后，色环切到"该色所在位置"，无彩色按 4.6 规则落圆心 | 取纯红像素，RGB 模式标记落在 0°，RYB 模式落在 0°，均在 1° 内 |
| FR-I9 | P2 | 图片取色预设：拖动取色吸管（跟随手指连续取样） | — |

**"滑动图片"的歧义澄清**：原始需求里"缩小/放大/滑动"应理解为"缩放 / 平移 / 拖动画面"，不是"滑动切换图片"。本版按前者实现；若确实想要**多图左右滑切**，属于 P2（见 11.2），因为它牵涉"一个项目是否有多个图"的数据模型变更，必须提前定。

### 5.3 色卡列表模块（Palette）

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| FR-L1 | P0 | 把当前色加入列表（自动命名 `颜色 1/2/3…`），重复色允许添加 | 加入 ≤ 200 ms；列表滚动到新项并高亮 0.6 s |
| FR-L2 | P0 | 每项显示色块 + 名称 + 当前模式数值；切模式时全部数值随之切换 | RGB 模式显示 `RGB(…)`，RYB 模式显示 `RYB(…)`；切换后无残留旧值 |
| FR-L3 | P0 | 重命名（点击名称原地编辑或弹窗），支持中文、长度 ≤ 24 字 | 空名自动回退原名；重名允许 |
| FR-L4 | P0 | **拖拽排序**，长按 300 ms 激活拖动，其余项让位动画 | 拖动时被拖项放大 1.05× 并抬起阴影；松手顺序立即持久化；≤ 50 项时不卡顿 |
| FR-L5 | P0 | 删除单项 + 撤销（5 s 内可撤销） | 删除后立即从列表移除；撤销恢复原位置与原名称 |
| FR-L6 | P1 | 卡片布局切换：大色块 / 列表 / 网格 | 三种布局均正确显示全部字段 |
| FR-L7 | P1 | **比对功能**：任选两色并排 + 色差 ΔE00 + 明度差 + WCAG 对比度 | ΔE 计算与参考实现误差 ≤ 0.5；对比度给出 AA/AAA 判定 |
| FR-L8 | P1 | 复制数值（HEX / RGB / RYB，长按菜单） | 复制到系统剪贴板可粘贴 |
| FR-L9 | P2 | 相似色提示（ΔE < 3 时角标"≈ 与 #3 接近"） | 不误报纯灰与纯白 |
| FR-L10 | P1 | 列表项点击 = 回选该色（色环标记跳回、预览更新） | 点击后环标记位置与该色数值一致 |

**拖拽排序的实现注意**：这是 Python 移动端最容易做砸的交互。Kivy 的 `RecycleView` 原生不支持拖动重排，需自写拖拽手势；务实用法是"列表项数有限（≤ 100）时用 `ScrollView + BoxLayout` + 自定义长按拖动"，比改造 RecycleView 成本低得多。此点写进 M1 的验收清单。

### 5.4 存档 / 历史记录模块（Project）

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| FR-S1 | P0 | **保存项目**：一次性保存"当前图片 + 完整色卡列表 + 排序 + 名称 + 当前模式 + 视图缩放位置" | 保存 ≤ 1 s（含图片落盘）；清单逐项核对无遗漏 |
| FR-S2 | P0 | 项目列表页：缩略图 + 名称 + 色数 + 更新时间；可打开、重命名、删除 | 打开后与保存时**逐项一致**（图片、色数、顺序、名称、数值） |
| FR-S3 | P0 | 自动保存草稿（每 30 s 或每次变更后 2 s 防抖），异常退出后可恢复 | 强杀进程后重开，提示"恢复上次工作"，恢复后数据不丢 |
| FR-S4 | P1 | 导出/导入：单个项目打包为 `.zip`（含 json + 图片），可分享到微信/网盘，也可再导入 | 导出文件在另一台设备导入后完全一致；损坏包给出提示而非崩溃 |
| FR-S5 | P1 | 数据校验与版本迁移：json 带 `schema` 版本号，图片带 hash | 篡改图片后打开提示"图片与记录不匹配"（不静默出错） |
| FR-S6 | P1 | 存储管理：显示占用、批量删除、剩余空间不足时警告 | 空间不足时保存失败但不丢当前内存数据 |
| FR-S7 | P2 | 多色板（一个项目内多组色卡，如"主色/辅助色/背景"） | — |

**为什么"保存图片"要单独强调**：多数学员项目只存路径，结果重启后路径失效、图片被删、换个机器打不开。本方案强制**把图片复制进 App 私有目录**，与原图脱钩，这是"存档可靠"的唯一简单解。

### 6.1 主界面布局（单页，三段式）

┌──────────────────────────────────────────┐
│  [RGB ●]  [ RYB ○ ]        模式切换       │  ← 顶栏
├──────────────────────────────────────────┤
│                                          │
│         ╭──────────────╮                 │
│        ╱   色  环        ╲      ┌────┐   │

│        ╲                ╱       │ ▓▓ │   │
│         ╰──────────────╯        │ ░░ │   │
│                                  └────┘   │

│   │ 预览 │  #2196F3   RYB(12,35,54)       │
│   └──────┘                                │
│                    [ ＋ 加入色卡 ]         │
├──────────────────────────────────────────┤

### 6.2 流程 A：色环取色并入库

1. 进入 App 默认落"色环"页 → 2. 拖标记或点环 → 3. 调明度滑杆 → 4. 点"加入色卡" → 5. 列表页看到新卡片（高亮 0.6 s）。

### 6.3 流程 B：图片取色并回显到环

1. 切"图片"页 → 2. 导入图片 → 3. 双指缩放定位到目标区域 → 4. **长按**目标像素（放大镜出现）→ 5. 微调 → 6. 抬手确认 → 7. 顶部自动提示"已取色，色环已定位" → 8. 切到色环页可见标记落在对应位置 → 9. 加入色卡。

**设计要点**：第 6 步抬手后不要立刻跳转页面（会打断连续取色），只在顶栏做一条 300 ms 的提示条 + 一个"看色环"按钮。取多个色时体验天差地别。

### 6.4 流程 C：存档与恢复

1. 项目页 → 2. "保存为项目" → 3. 输入名称（默认"未命名 10-29"）→ 4. 保存 → 5. 项目列表出现缩略图 → 6. 杀进程 → 7. 重开 App → 8. 自动恢复上次会话；或在项目页手动打开任一项目。

## 7. 技术可行性分析

### 7.1 框架选型（Python → Android 的现实选项）

> **2026-10-29 已改判**：选型结论已由 [`技术方案-框架选型.md`](技术方案-框架选型.md) 替代。
> 放弃 Kivy/Buildozer，改为复用 `e2046价格监测` 已验证的 **Gradle + Chaquopy + WebView** 流水线。
> 下表保留作为决策依据的留档。

| 方案 | 能否出 APK | 图形/手势能力 | UI 与列表能力 | 桌面可跑 | 风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **Kivy 2.3+ / KivyMD + Buildozer(p4a)** | ✅ 成熟 | ✅ 强：Canvas、Mesh、Scatter（现成缩放平移）、纹理操作 | ⚠️ 一般：UI 偏旧，RecycleView 拖拽需自写 | ✅ Windows 直接跑 | 构建链脆弱、包体 ~25–40 MB | **主选** |
| Flet（Flutter 外壳 + Python 运行时） | ✅ `flet build apk` | ⚠️ 中：有 Canvas/渐变，但像素级取色与手势坐标映射绕 | ✅ 强：ReorderableListView、FilePicker 现成 | ✅ 极简 | 依赖 Flutter SDK（~1 GB）；变换矩阵不好拿 | 备选 |
| BeeWare / Toga + Briefcase | ✅ | ❌ 弱：无自定义色环绘制 | ⚠️ 原生控件但生态小 | ✅ | Android 端控件与手势不成熟 | 不推荐 |
| Chaquopy（Android Studio + Python） | ✅ | 取决于 Java 侧 | 取决于 Java 侧 | ❌ 不能直跑 | 变成"Java 壳 + Python 逻辑"，与"Python 开发"初衷不符 | 不推荐 |
| PySide6 + p4a | ❌ | — | — | ✅ | 官方不支持 Android | 排除 |

**推荐 Kivy 的决定性理由**：本 App 的难点全在**自绘与手势**（色环纹理、放大镜、图片变换），这正是 Kivy 的强项；而它的弱项（列表、文件选择）都有已知解法，工作量可估。Flet 则相反：列表和文件选择白送，但自绘与坐标映射要还债。**先难后易**更安全。

### 7.2 架构分层（推荐）

```
┌─────────────────────────────────────────────┐
│ UI 层（Kivy 屏幕/控件）  ← 唯一依赖平台的层    │
├─────────────────────────────────────────────┤
│ 应用服务层：状态机、命令（Undo/Redo）、会话    │
├─────────────────────────────────────────────┤
│ 色彩内核 colorcore（纯 Python + numpy）      │
│  · rgb↔hsv  · rgb↔ryb  · 色环纹理生成        │
│  · ΔE00  · 命名色匹配  · 数值解析/格式化      │
├─────────────────────────────────────────────┤
│ 图像服务 imageio（Pillow）                   │
│  · 解码/EXIF/降采样/像素采样/缩略图/放大镜裁切 │
├─────────────────────────────────────────────┤
│ 仓储层 repo（纯 Python）                     │
│  · 项目 json 序列化、目录管理、zip 导入导出    │
├─────────────────────────────────────────────┤
│ 平台适配层 platform（Kivy/Android 各一份）    │
│  · 选图 · 导出位置 · 分享 · 剪贴板 · 存储路径  │
└─────────────────────────────────────────────┘
```

**为什么这样切**：`colorcore` / `imageio` / `repo` 三层在 Windows 上用 pytest 全量测，CI 里不需要模拟器；Android 侧只剩"UI + 平台适配"，出问题时能立刻判定是逻辑 bug 还是平台问题。

### 7.3 关键算法与性能预算

| 环节 | 做法 | 预算 |
| --- | --- | --- |
| 色环纹理 | numpy 一次性算 `128×128`（或 `192×192`）RGBA，转 Kivy Texture；明度变化时重算（限制 15 fps 重算，视觉够用） | 128² 单帧 2–6 ms |
| 环上取色 | 由触点坐标反算 (θ, ρ)，不做像素读回（比 glReadPixels 稳、跨 GPU 一致） | < 1 ms |
| 图像点选 | 触点 → 视图坐标 → 图片坐标（用自己维护的 scale/offset，不读 Scatter 矩阵，避免累积误差）→ 采样 | < 1 ms |
| 放大镜 | 从已解码的 numpy 数组裁 32×32 区域，放大成 96×96 纹理 | < 5 ms，可 30 fps 跟手 |
| RGB→RYB | 4913 点向量化最近邻 + 局部细化 | 1–4 ms |
| 图片解码 | Pillow `draft()` 降采样 + `ImageOps.exif_transpose`；上限 2048 px 存副本 | 4000 px 图 ≤ 1.2 s |
| 存档 | json + 图片文件 + 缩略图，原子写（临时文件 → rename） | ≤ 1 s |

**大图内存策略**：解码上限 2048×2048（约 16 MB RGB）；更精细的取色需求靠"原图重新采样"实现而非保留全图，避免低端机 OOM。这是取舍，需在文档里写明（见 12-Q4）。

### 7.4 Android 构建链路（Python 的现实约束）

**核心事实**：`buildozer` / `python-for-android` **不支持 Windows 直接构建**。所以"GitHub 在线编译"不是可选项，而是必需项。

| 环节 | 方案 | 备注 |
| --- | --- | --- |
| 构建机 | GitHub Actions `ubuntu-22.04` | 24.04 亦可，但 22.04 的 Android SDK 组合更稳 |
| Python 版本 | **打包侧按 p4a 支持版本锁定**，桌面侧用 3.12.0（已本机确认） | 两者的 Python 版本解耦，别为了"都是 3.12"去啃 p4a recipe |
| JDK | 17 | p4a/Gradle 现行要求 |
| SDK/NDK | 由 buildozer 自动下载（首次约 2–3 GB） | 必须缓存，否则每次 25–40 min |
| 缓存 | `~/.buildozer`、`~/.gradle`、`~/.cache/pip` | 命中后二次构建 6–12 min |
| 产物 | debug APK + release APK（可选 AAB） | 上架 Play 才需要 AAB |
| 签名 | keystore 放 GitHub Secrets（base64），构建时解码 | 绝不能提交 keystore |
| targetSdk | 跟随 Google Play 当年要求（2025-08 起 35；2026 年预计 36） | 只在发布前关注，MVP 阶段 fixed 到 34/35 即可 |
| 架构 | `arm64-v8a` 为主，`armeabi-v7a` 可选 | 只打 arm64 可省 ~40% 体积，覆盖绝大多数在用设备 |

**首次构建的真实体验**：20–40 分钟，失败率高（NDK 版本、pip 源、依赖 C 扩展）。**必须在 M0 就打通，不要等到功能做完才发现打不出包**——这是 Python 移动开发最容易翻车的地方。

### 7.5 文件与存储（Android 权限的坑）

| 场景 | 方案 | 权限 |
| --- | --- | --- |
| 应用自己的项目数据 | 私有目录 `app_storage/projects/…` | 无 |
| 选择图片 | Android 13+ 用系统 Photo Picker（`ACTION_PICK_IMAGES`）；旧版本 `ACTION_OPEN_DOCUMENT` | **零权限**（比申请 `READ_MEDIA_IMAGES` 体验好得多） |
| 导出 zip 到用户可见位置 | `ACTION_CREATE_DOCUMENT`，用户自选路径 | 零权限 |
| 分享 | `ACTION_SEND`（FileProvider） | 零权限 |

**技术债提醒**：Kivy 侧没有开箱即用的 SAF 封装，需要用 `jnius` 调 `Intent` 并处理 `on_activity_result` 回调（社区有成熟配方，约 100–150 行）。这是 M0 必须验证的第二件事；若验证失败，退路是"仅存私有目录 + 通过分享导出"，功能不减，只是用户拿不到文件。

### 7.6 风险矩阵

| # | 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- | --- |
| R1 | p4a 首次打包失败/耗时失控 | 高 | 高 | M0 优先打通；锁版本；缓存；备选 docker 镜像 |

## 9. 数据模型

### 9.1 项目文件结构

```
app_storage/
├── index.json                     # 项目索引（轻量，列表页只读它）
├── autosave/session.json          # 崩溃恢复
└── projects/
    └── <project_id>/
        ├── project.json           # 主数据
        ├── image.jpg              # 项目内副本（≤2048px）
        └── thumb.jpg              # 256px 缩略图
```

### 9.2 project.json

```json
{
  "schema": "colorpick/project@1",
  "id": "6f1c2a3e-...",
  "name": "秋日海报参考",
  "created_at": "2026-10-29T10:12:00+08:00",
  "updated_at": "2026-10-29T10:40:11+08:00",
  "mode": "ryb",
  "image": {
    "file": "image.jpg",
    "width": 2048,
    "height": 1536,
    "origin_name": "IMG_20261029_101200.jpg",
    "sha256": "9f2c…"
  },
  "view": { "scale": 1.0, "offset_x": 0.0, "offset_y": 0.0 },
  "settings": { "sample_size": 1, "brightness": 0.86, "wheel_ticks": true },
  "palette": [
    {
      "id": "c_01",
      "name": "雾蓝",
      "order": 0,
      "rgb": [122, 158, 189],
      "ryb": [24, 31, 45],
      "source": { "type": "image", "x": 812, "y": 431, "sample": "1x1" },
      "created_at": "2026-10-29T10:20:03+08:00"
    }
  ]
}
```

**设计要点**

- `rgb` 是**唯一真值**，`ryb` 是缓存值（加载时可用 `rgb` 重算，防止算法升级后旧数据失真）——但保留字段以便跨版本比对和迁移。
- `source` 记下取色来源坐标，使"回到原图位置"成为可能（P2 亮点功能）。
- `order` 显式存，避免依赖数组下标（拖拽排序后重排数组会丢信息，尤其在部分失败写入时）。
- `schema` 版本号 + `sha256` 是"未来不背锅"的两块保险。

| **M4 打磨发布** | 引导、双语、图标、关于页、签名 release、崩溃日志 | 装机走查无 P0/P1 缺陷；Release APK 可安装 | 4–6 人日 |

**总计 26–38 人日**（含返工余量）。若只有业余时间，按 **1.5–2 倍** 估。

## 11. 改进方向（按性价比排序）

### 11.1 强烈建议纳入（低成本、高收益）

1. **放大镜精选取色**（已作为 P0）。原始需求只说"点击取色"，但手指宽度约 8–10 mm，在小图上点选误差可达几十像素。放大镜是本产品能不能"准"的分水岭，且实现成本仅半天。
2. **色环 + 明度滑杆**（已作为 P0）。二维环给不出深色/浅色，用户第一次想取"深藏青"就会卡住。
3. **取色后不跳页，只提示**（见 6.3）。连续取色的场景下，跳页会让人想砸手机。
4. **"估算"说明 + 校准入口**。RYB 算法自己定的，必须诚实。可选给个"高级设置"让人微调角点（插画师会很买账）。
5. **ΔE 比对**（P1）。需求里写"方便比对"，人眼比对不如给个数字。ΔE00 + 双色并排 = 一句话说清"这两个色差多少"。
6. **原子写 + 自动草稿**。存档类 App 的口碑全在"不丢数据"。
7. **零权限选图**。比申请存储权限省事，也让"隐私安全"成为卖点。

### 11.2 值得考虑（中等成本）

8. **多图项目 / 多色板**：一个项目里"主色/辅色/背景"分组，或一张参考图配多张色卡。**注意这会影响数据模型，需在 M1 前定**（见 12-Q1/Q2）。
9. **色名匹配**：给出近似色名（CSS 色名、中国传统色、日本传统色）。中国传统色库对中文用户吸引力极大（"天青""黛蓝"），且是纯数据活儿，成本低。
10. **导出为图片/设计文件**：色板导出 PNG 卡片（可分享）、ASE（Adobe 色板）、GPL（GIMP/Krita）。设计师愿意为此付费。
11. **从色卡反推"怎么调"**：给定目标色与当前色，用 RYB 立方体算"再加 X% 黄、Y% 蓝"。这是本产品真正的差异化功能，但算法要小心（多解），建议 V2。
12. **色盲模拟预览**（3 型），帮设计师自检。

### 11.3 长期（暂不排期）

13. 相机取景器实时取色（每帧取样，Python 端可能吃力，需原生侧配合）。
14. 配色方案推荐（互补/三角/邻近），基于色相角自动生成。
15. 项目云同步（引入后端，成本陡增，慎入）。
16. 平板/折叠屏双栏布局。

### 11.4 明确"不做"的诱惑

- **别一开始就做 iOS**：Briefcase/Kivy 的 iOS 链路比 Android 更磨人，且需 Mac。
- **别用 Web 技术栈（Kivy WebView/PyScript）替代原生方案**：包体与性能都不划算，且离线文件体验差。
- **别过度设计色彩管理（ICC/CMYK）**：目标用户不需要，实现成本极高。

## 13. 竞品与差异点（简要）

| 类型 | 代表 | 强项 | 缺口 |
| --- | --- | --- | --- |
| 取色吸管 | Color Grab 类 | 相机实时取色、色号识别 | 只有 RGB/HSV，无颜料视角 |
| 配色工具 | Adobe Color / Coolors | 配色方案生成、社区 | 不做"从图取色 + 存档还原"，无 RYB |
| 色卡管理 | 各类色板 App | 命名、分类 | 不做双模型换算，无法从图精确定位 |

**本产品的差异点就一句话**：*"取到的颜色，能立刻用颜料语言读懂，并且能存成可回溯的色板项目。"* 功能清单里只有"双色环 + 图片取色 + 存档"三者同时具备时才有意义，缺一个就退化成普通工具。

## 15. 一页纸结论

- **能做**，且不需要引入任何服务端。
- **顺序必须是**：先验证打包链路（M0）→ 再堆功能（M1–M3）→ 最后打磨发布（M4）。**倒过来必然返工。**
- **三个必须新增的设计**（原始需求里没有，但不加会难用）：明度滑杆、放大镜、**参照色比对（双标记环 + 一致/不一致徽标）**。
- **三个必须先定的决策**：① 光色环色相用 OKLCH 还是 HSV；② "色相一致"的阈值（±3° / ±8°）；③ 是否上架 Play。
- **最大风险只有一个**：Python → Android 的构建链路。它决定了这个项目是"两周出包"还是"两个月出包"，所以 M0 只有这一个目标。
