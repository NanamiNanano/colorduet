## 1. 产品定义

### 1.1 一句话

**取到的颜色，能立刻用颜料语言读懂，并且能存成可回溯、可比对的色板项目。**

### 1.2 问题

设计师在屏幕上取色，拿到的是一串 RGB，靠肉眼猜"偏暖还是偏冷、跟上一个差多少"；画师想的是"红加黄偏橙、再加点蓝会变灰"，这是颜料体系，而所有取色工具只给 RGB/HSV。两套语言之间没有桥。

### 1.3 目标用户

自己（插画/设计/手作场景），以及任何"既要屏幕配色、又要调颜料"的人。

### 1.4 成功标准

- 打开到取出第一个色并入库 ≤ 4 次操作、≤ 15 秒。
- 图片点选到色环标记更新 ≤ 100 ms。
- 色环拖动、图片缩放稳定 ≥ 30 fps。
- 存档后杀进程重开，图片与色卡 100% 还原。
- 同一颜色的 RGB 与颜料坐标，三处（环、卡片、存档）一致。

### 1.5 非目标

云同步、账号、社区、相机实时取色、印刷级色彩管理（ICC/CMYK/专色）、iOS、多图层编辑。

## 2. 关键概念：为什么必须有两个环

"补色"在中文里被三种关系共用，这是最容易设计错的地方。

| 叫法 | 怎么算补色 | 红色对面 |
| --- | --- | --- |
| 光学补色 | 光相加变白 | **青** |
| 颜料补色 | 颜料相加变暗浊 | **绿** |
| 对立色（Hering） | 神经对抗 | 绿（但黄↔蓝） |

**最直观的证据（可做引导页文案）：**

| 混合 | 光（相加） | 颜料（相加） |
| --- | --- | --- |
| 黄 + 蓝 | **白**（是补色对） | **绿**（不是补色） |
| 红 + 绿 | **黄**（不是补色） | **暗浊灰**（是补色对） |

同一对颜色，两种混合下"是否互补"的答案完全颠倒。**这就是双环存在的唯一理由。**

> **陷阱**：真正的"减色"是 CMY（印刷），而 CMY 就是 RGB 的反相，补色关系完全相同（青↔红）。若把第二个环做成"减色 CMY"，它会和第一个环一模一样。所以第二个环必须是 RYB，术语上也别叫"减法模式"，叫**颜料环**。

## 3. 色彩模型规范

### 3.1 两环一览

| | 光色环（Light） | 颜料环（Pigment） |
| --- | --- | --- |
| 形态 | **空心环**（内径 0.80 / 外径 1.0），只有色相 | 同 |
| 角度 | HSV 的 H：红/黄/绿/青/蓝/品红，**每 60° 一个** | 颜料色相：红/橙/黄/绿/蓝/紫，**每 60° 一个** |
| 环本身 | 恒定 `S=1, V=1`（纯色相参考，不随滑杆变暗） | 同 |
| 饱和度 | **独立滑杆** | 独立滑杆 |
| 明度 | **独立滑杆** | 独立滑杆 |
| 补色对 | 红↔青　黄↔蓝　绿↔品红 | 红↔绿　黄↔紫　蓝↔橙 |
| 颜色来源 | `HSV(H, S, V)` | 把 HSV 色相轴按 RYB 顺序重排后的 `HSV(H′, S, V)` |

**两环共性**：环只负责色相；饱和度与明度各有独立滑杆，**两条滑杆的轨道颜色随当前选色实时变化**（饱和度条 = 当前色相下 灰→艳；明度条 = 黑→当前色相最亮）。
切换模式时**严格保持颜色不变**，只有环上的角度被重算——因为两模式的 S/V 语义完全相同，所以这是精确保持，不是近似。

**为什么把饱和度从半径里拿出来**：一旦半径被饱和度占用，色环就无法表达"同一色相、不同明度纯度"的细微差别，且中心区域的触控精度很差（越往圆心，同样 1px 对应的饱和度变化越大）。拆开之后：环管色相、滑杆管另两维，三者互不干扰，取值也更准。

参考图：`preview/01-hsv-vs-oklch.png`（左为光色环）、`preview/04-ryb-wheel.png`（颜料环）。

### 3.2 颜料环的算式（**实现已改，见下方说明**）

**最终方案：色相轴重排。**

- 把 HSV 的色相轴按画家习惯重新排列：颜料角 0/60/120/180/240/300（红/橙/黄/绿/蓝/紫）分别对应 HSV 色相 0/30/60/120/240/285。
- 用**单调三次插值（PCHIP）**在锚点之间过渡，保证 C1 连续——否则每个锚点会出现一条可见"折痕"。
- 饱和度、明度完全沿用 HSV，因此：**双向精确（往返误差 0°）、无任何色域损失、6 组补色严格对径**。
- 颜料"配比"由角度按 6 锚点线性插值得到，再乘以饱和度（无彩色的配比没有意义，显示"近乎无彩"）。

**为什么不直接用 RYB 立方体（早期方案，已弃用）**

| 指标 | RYB 立方体 | 色相轴重排 |
| --- | --- | --- |
| 能表示多少 sRGB 颜色（ΔE00 ≤ 3） | **40.3%** | 100% |
| 往返误差中位 / 最差 | 4.3 / 22.7 | 0 / 0 |
| 环的观感 | 偏暗、发闷 | 与光色环同样鲜艳 |
| "红+黄=橙"的混色预测 | ✅ 有 | ❌ 无（属于后续"混色预测"功能） |

立方体的致命问题：它的色域是 8 个角点围成的凸包，比 sRGB 小得多。取一个纯绿像素，它在颜料环上根本没有对应位置（最近的也要差 ΔE 22）。而"从图片取色 → 显示在环上"是核心需求，不能打折。
**结论**：环用色相轴重排；立方体函数保留在 `color.js` 里，将来做"这两个色混起来大概是什么"时再用。


### 3.3 无彩色的落点

| 输入 | 光色环 | 颜料环 |
| --- | --- | --- |
| 纯灰 | 圆心，S = 0 | 圆心，纯度 = 0 |
| 纯黑 | 圆心，V = 0 | 圆心 + 加黑 100% |
| 纯白 | 圆心，V = 100% | 圆心 + 加白 |
| S < 3% | 吸附到圆心（可关） | 同 |

### 3.4 数值展示（折叠）

- 主显示（卡片正面）：色块 + 名称 + 徽标。
- 展开后：`HEX` / `RGB(…)` / 颜料坐标 `(r, y, b)%` / 色相角 / L\*。
- **颜料三元组不做归一化**（三项和不必为 100），否则丢失"颜料很浓"的信息。

### 3.5 比较口径与冲突规则

| 维度 | 指标 | 一致 | 接近 | 不同 |
| --- | --- | --- | --- | --- |
| 色相 | 当前环的角差 \|Δh\| | ≤ 3° | 3–10° | > 10° |
| 明度 | ΔL\*（0–100） | ≤ 2 | 2–5 | > 5 |
| 彩度 | ΔC（OKLCH） | ≤ 0.015 | 0.015–0.04 | > 0.04 |
| 总差 | ΔE00 | < 2 | 2–5 | > 5 |

**冲突规则（重要）**

- 色相判"一致"但 ΔE00 > 5 → 显示"色相接近，但整体差异明显"（通常是明度/彩度差太多）。
- 色相判"不同"但 ΔE00 < 2 → 显示"肉眼接近"（HSV 角差在此色区偏敏感）。
- **原则**：ΔE00 负责"看起来差多少"，色相角负责"往哪个方向调"。

## 5. 界面与流程

### 5.1 主界面

```

│  [光色环 ●]  [颜料环 ○]     ? │

│  色卡（拖动 ⠿ 排序 · 双击改名） │
│  ⠿ ██ 雾蓝   ✓3°  -12    ×    │
│  ⠿ ██ 赭石   ✗18° +5     ×    │
└──────────────────────────────┘
```

### 5.2 流程 A：色环取色入库

拖标记 → 调明度 → 点"加入色卡" → 列表高亮新项。

### 5.3 流程 B：图片取色

切图片页 → 导入（可多张）→ 双指缩放定位 → **长按**出放大镜 → 微调 → 抬手确认 → 顶栏提示"已取色，环已定位"（**不跳页**，避免打断连续取色）。

### 5.4 流程 C：存档恢复

保存 → 项目列表出现缩略图 → 杀进程 → 重开自动恢复草稿，或手动打开项目。

## 6. 技术架构

```
┌────────────────────────────────────────────┐
│ WebView（Android）/ 浏览器（PC）             │
│  index.html + app.js + color.js + style.css │
│  · Canvas 2D：双环、放大镜、图片、点云       │
│  · Pointer Events：缩放/平移/长按/拖拽       │
│  · 色彩数学全部在前端（要 60fps）            │
└──────────────┬─────────────────────────────┘
               │ HTTP /api（仅本机）
┌──────────────┴─────────────────────────────┐
│ Python 标准库 http.server（无 pip 依赖）     │
│  · 静态文件 · 项目 JSON · 图片落盘（base64） │
│  · zip 导入导出 · 备份                       │
└──────────────┬─────────────────────────────┘
               │
   PC: ./data/        Android: getFilesDir()/colorpick/
```

**分工原则**：交互与计算在前端（要快），持久化在 Python（要可靠）。因此 APK 里**不需要 numpy / Pillow / 任何 pip 包**，Chaquopy 构建快且稳。

### 6.0 M0 实际实现：Android 端暂时不用 Chaquopy

| 端 | 形态 | 原因 |
| --- | --- | --- |
| PC | `python -m colorpick`（本地服务 + 浏览器） | 开发调试方便，改完刷新即可 |
| Android | **纯 WebView 壳，直接加载 `assets/www/index.html`** | 当前前端是纯静态，没有需要 Python 的东西 |

**为什么 M0 不塞 Python 进去**：Chaquopy 会让 APK 多 20 MB、构建慢一倍，而现在它一行代码都不跑——纯属负重。Python 的真正职责是"项目存档落盘"，那要等 M4；届时按需加回来，且是加法（加插件 + 加 python 目录 + 桥接），不改动已有的壳。

**这条链路的取舍**：`file:///android_asset` 直接加载省掉了"Python 起 HTTP 服务 + 把 assets 复制到私有目录"的一整圈麻烦，代价是不能用 `fetch`/XHR（我们本来也不用），以及 **`file://` 下 localStorage 的持久性需要在真机上验证**——如果实测不保存，退路是把页面改成由本地服务提供（Chaquopy 或 Java 侧起 server），或者把存储换成 IndexedDB。

## 7. 数据模型

```
data/
├── index.json                    # 项目索引
├── autosave/session.json         # 崩溃恢复
└── projects/<id>/
    ├── project.json
    ├── images/img_01.jpg …
    └── thumbs/img_01.jpg …
```

```json
{
  "schema": "colorpick/project@1",
  "id": "6f1c…",
  "name": "秋日海报",
  "created_at": "…", "updated_at": "…",
  "mode": "light",
  "images": [
    { "id": "img_01", "file": "images/img_01.jpg", "w": 2048, "h": 1536,
      "origin_name": "IMG_0001.jpg", "sha256": "…", "thumb": "thumbs/img_01.jpg" }
  ],
  "active_image": "img_01",
  "view": { "img_01": { "scale": 1.0, "x": 0, "y": 0 } },
  "compare_ref": "c_03",
  "palette": [
    { "id": "c_01", "name": "雾蓝", "order": 0,
      "rgb": [122, 158, 189],
      "source": { "image_id": "img_01", "x": 812, "y": 431, "sample": 1 } }
  ]
}
```

**原则**

- `rgb` 是唯一真值；颜料坐标与 OKLCH **全部派生**，不落盘（算法改了重算即可）。
- `source.image_id` 必填，否则多图下会丢"从哪张图取的"。
- `order` 显式存，不信数组下标。
- `schema` 版本号 + 图片 `sha256` 是两块保险。

## 11. 风险登记册

| # | 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- | --- |
| R1 | WebView 里 Canvas 逐像素画环太慢 | 中 | 中 | 环纹理一次性生成后缓存，明度用黑色叠层（数学上等价于乘 V），不重绘 |
| R2 | 安卓 WebView 的 `onShowFileChooser` 行为差异 | 中 | 高 | M0 第 3 天专门验证；退路：用 `ACTION_OPEN_DOCUMENT` 直连 |
| R3 | WebView 不支持 HTML5 拖拽 | **高** | 中 | 已知：**必须用 Pointer Events 自写排序**（已在 FR-L4 固化） |
| R4 | 中文输入 / 长按选中文本干扰 | 低 | 中 | CSS `user-select`、`touch-action` 精确控制 |
| R5 | 颜料立方体中心偏褐，观感像 bug | 高 | 中 | 界面加一行说明；P1 做中轴校正 |
| R6 | HSV 的 ±3° 在绿区不敏感、黄区过敏 | 高 | 低 | ΔE00 兜底 + 冲突规则（3.5） |
| R7 | 大图内存（WebView 解码） | 中 | 中 | 导入即降到 2048 px 再走 canvas |
| R8 | 无真机，问题只能靠装机发现 | 中 | 中 | 每个里程碑出 APK 装机走查，关键流程录屏 |
